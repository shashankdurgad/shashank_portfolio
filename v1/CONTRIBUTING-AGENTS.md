# Working on this site

Notes for anyone — human or agent — picking this codebase up cold. It is
written from the experience of building the current scene, and concentrates on
the things that are **not** discoverable by reading the code: traps that cost
hours, invariants that are easy to break silently, and testing methods that
actually work here.

`AGENTS.md` is generated by `next dev` and re-added automatically. Do not
hand-edit it; commit it with your work if it shows up dirty.

---

## 1. What this site is

A single-page portfolio built around one continuous 3D sequence. Everything is
one particle system whose targets change — particles never spawn or die, which
is what makes the whole thing read as the same matter rearranging.

```
scroll ──────────────────────────────────────────────────────►
  hero            morph region                doors      (inside a door)
  eyes  →  explosion  →  halo + doors  →  [click] →  flight → timeline
```

| Stage | Driven by | Where |
|---|---|---|
| Eyes (gaze, blink) | idle + cursor | `lib/eyeGeometry.ts`, `lib/eyeTargets.ts`, `lib/gaze.ts` |
| Explosion | `scroll.morph` 0→1 | procedural, in `morph.glsl.ts` |
| Halo + doors | `scroll.morph` 1→2 | `lib/haloTargets.ts`, `lib/doors.ts`, `Doors.tsx` |
| Flight through a door | click, then a clock | `lib/doorStore.ts`, `Rig.tsx` |
| Timeline traverse | `scroll.timeline` 0→1 | `lib/timelineCurve.ts`, `Timeline.tsx` |

The **right-hand door ("Projects") is a stub.** It opens but leads nowhere, and
clicking it deliberately does not start a flight — there is nothing behind it,
so the camera would fly into empty space. That is the obvious next feature.

## 2. Read this before you touch the 3D

These are the ones that will waste your afternoon.

### The canvas is `pointer-events: none`

`SceneCanvas.tsx` sets it so the HTML above stays clickable. The consequence:
**R3F's own hit-testing does not work.** `onPointerOver` / `onClick` on a mesh
will never fire for anything the page content covers, and page content covers
almost everything.

Two workarounds are already in the codebase — copy whichever fits:

- **Screen-space picking** (`Timeline.tsx`, `useNodeHover`): project the object
  to screen coordinates each frame and compare against a pointer position
  tracked from a plain `window` listener. Gives you a hit radius in *pixels*,
  which is usually what you want anyway.
- **Window pointer + manual raycast** (`MorphField.tsx`): track the pointer on
  `window`, build NDC yourself, and call `raycaster.setFromCamera`.

The doors are the exception — they *do* use R3F events, because they sit in a
region with no HTML over them. Do not assume that generalises.

### Additive particles cannot render surfaces

`blending: AdditiveBlending`, no lighting, no depth sorting. This is excellent
for **lines, edges, glows and outlines** and hopeless for **volumes and
surfaces**. There is no shading channel, so nothing you do to the geometry will
produce a lit ridge or a shadowed groove.

This is not a tuning problem, and it has already sunk two designs. If a new
stage needs a solid form with hard edges — a panel, a slab, a face — make it
**geometry** and let the particles be the atmosphere around it. That is exactly
what the doors do.

### `scroll.morph` clamps at 2 and stays there

`ScrollController.tsx` maps the morph region's 0..1 onto 0..2. Once you are
past that region it sits at 2 forever. Anything keyed only on `morph` will
therefore never turn off again — this caused the doors to remain mounted into
the timeline, where the camera then flew through them at point-blank range.

If you add something that must disappear later, key it on the *later* stage's
progress as well. See `leaving` in `MorphField.tsx`.

### Lenis owns scrolling

- `window.scrollTo()` **does not drive the page.** ScrollTriggers will not
  update. Use `window.__lenis.scrollTo(...)`.
- Lenis **caches document height** and silently clamps any target to it. If you
  have just changed the page height — as entering a door does — call
  `resize()` first or your scroll will be requested, clamped, and go nowhere
  with no error.
- After changing any section's height, call `ScrollTrigger.refresh()`, or every
  trigger below it keeps stale measurements.

### Per-frame values must not go through React

`lib/scrollStore.ts` is a plain mutable object, deliberately outside React.
Routing per-frame values through `useState` re-renders the tree 60×/second.

The corollary bites: **never read a ref during render** to derive per-frame
state. It will freeze at whatever it was when the component last rendered.
Compute it inside `useFrame` and write to the object/material directly. The
timeline nodes were built wrong this way first — they simply never animated.

### The eslint immutability rule

`react-hooks/immutability` fires on the standard R3F pattern of mutating
uniforms in `useFrame`. Existing code disables it narrowly, at the `useFrame`
call site. Prefer restructuring so the rule passes — owning mutable GPU objects
in a `useRef` built on first frame works — and suppress only when the rule is
genuinely wrong. A blanket disable hides real bugs.

## 3. Invariants you must not break

**Every morph target buffer is exactly `N*3`, same `N` as every other stage.**
The vertex shader lerps index-to-index between `position`, `aTree` and
`aThread`. A mismatched length tears the morph apart. `N` comes from
`PARTICLES` in `lib/morphTargets.ts` (70k high / 20k low).

**`aSide` is strictly −1 or +1.** It drives which door is hovered, the hover
highlight, and the halo's drift. Anything else silently breaks all three.

**`TIMELINE_ORIGIN` has one source.** `Timeline.tsx` exports it, `Rig.tsx`
imports it. Keep it that way: the camera reads positions off the same curve the
thread is drawn from, so if the two ever disagree the camera flies *alongside*
the thread rather than along it.

**Dependency direction is one-way:** flight → timeline. `Rig` and `MorphField`
read the timeline's curve. The timeline must **not** import `lib/doorStore.ts`
— that was a genuine cycle, and it is why flight progress lives in
`scroll.doorFlight` rather than next to the door's own state.

## 4. Testing this thing

Screenshots lie here more than usual. Several "it's broken" conclusions in this
codebase were wrong, and several "it works" conclusions were too.

### Dev hooks

All guarded by `process.env.NODE_ENV !== "production"`:

| Hook | Gives you |
|---|---|
| `window.__field` | camera position, morph, gaze, blink, doors, cursor |
| `window.__tl` | timeline raw/progress/visible |
| `window.__doorAngle` | the left door's actual rotation |
| `window.__lenis` | the Lenis instance |

Add to these rather than reasoning from pixels. Most of the hard bugs here were
found by printing a number, not by looking.

### Driving the page in a headless browser

- **Use `mouse.wheel`, not `window.scrollTo`** (see Lenis, above). Several
  early tests concluded "the morph is broken" when they had simply never
  scrolled it.
- **Wait for a state, not a duration.** `waitForFunction(() => window.__tl.visible > 0.9)`
  beats a fixed timeout. Lenis eases for ~1.5s after the wheel stops, so a
  screenshot taken too early catches a scene mid-transit.
- **Catch console errors, not just `pageerror`.** three.js reports **shader
  compile failures as console errors**. A test listening only for `pageerror`
  will cheerfully report "no errors" while the scene renders nothing at all.

### Two techniques worth reusing

- **Screen-space density map** — project all particles onto the camera plane
  and print an ASCII heat map. This is what revealed that a shape was a hollow
  ring; a bounding box cannot see through a form.
- **Per-column silhouette profile** — for each x, print min/max y. This caught
  a "wing" that was actually a constant-width band.

### SwiftShader caveat

There is no GPU in the usual test environment. Additive blending renders much
flatter than on real hardware, and anything above DPR 1 collapses — so **frame
rate cannot be measured here at all**. Estimate fill rate instead, and say
plainly that timings need a real machine.

## 5. Layout and scroll structure

```
#hero      100vh   Hero copy. Canvas is behind everything.
#morph     320vh   eyes → explosion → doors
#timeline    0     until a door is entered, then 360vh
```

The timeline section having **zero height until entered** is what stops the
page continuing past the doors into a section nobody chose to open. While
inside, scrolling is floored at the section's top (`clampFloor` in
`ScrollController.tsx`) so the Back control is the only way out — otherwise
scrolling up unwinds the morph and you get the eyes reforming *over* the
timeline.

Copy also lives as real DOM in each section (`sr-only` where it duplicates 3D
labels). The canvas is presentation; the HTML is the actual record, and it is
all that search engines and screen readers see.

## 6. Quality tiers and accessibility

`lib/quality.ts` picks `high` / `low` / `off`:

- `off` for `prefers-reduced-motion` **or** no WebGL — the canvas never mounts.
  Check this still holds after any scene change; it is the one that matters.
- `low` for coarse pointers or ≤4 cores.

Note the tier heuristic is crude — core count says nothing about GPU. If a user
reports a poor-looking scene, get `navigator.hardwareConcurrency` and
`devicePixelRatio` before assuming anything.

**DPR gotcha:** R3F's `calculateDpr` *clamps* `devicePixelRatio` into whatever
`[min, max]` you give it, so an array can never render *above* native density.
Supersampling a 1× display needs a scalar. `renderScale()` in `SceneCanvas.tsx`
does this.

## 8. Legacy names, and checking for dead code

**Names that are not what they say:** `aTree` and `uTreeMix` date from when the
final stage was a pair of fractal trees. They mean *final-stage target* and
*final stage has formed*. Renaming touches several files for no behavioural
gain; the shader header documents this.

The scene has been rebuilt several times — a bust, a brain, wings, a swarm —
and each pass tends to strand a module. Before deleting anything, check both
the import and the symbols it exports, since a module can be dead while a name
it exports lives on elsewhere:

```bash
grep -rn '@/lib/<name>' app components lib          # imports
grep -rn '\b<ExportedSymbol>\b' app components lib  # uses of what it exports
```

Watch for matches inside comments — prose mentioning an old approach is not a
dependency. That is the difference between a safe delete and a broken build.

## 9. Working style that paid off here

- **Measure before you tune.** The productive loop was: form a hypothesis,
  print a number that would falsify it, then change one thing. Guessing at
  constants cost far more time than any instrumentation did.
- **Sweep parameters instead of guessing.** One shape had a usable window of
  only 0.30–0.40; five guesses missed it and a sweep found it immediately.
- **Verify each commit builds standalone**, not just the tip — `git worktree
  add` to a temp dir and build there. Splitting on file boundaries rather than
  dependency boundaries produced broken intermediate commits twice.
- **Check the test before believing the failure.** More than one "bug" here was
  a test scrolling with `window.scrollTo`, screenshotting mid-transition, or
  listening for the wrong error type.

## 10. Quick checklist before you finish

```bash
npx tsc --noEmit          # types
npx eslint .              # lint
npx next build            # production build
```

Then, in a browser, walk the whole sequence:

- hero → eyes track the cursor and blink
- scroll → explosion is formless, no leftover shape
- doors appear, hover peeks, click flies through
- timeline: camera moves on the *first* scroll, card tracks the nodes
- scroll back → clamps at the timeline start, eyes do **not** reappear
- Back → flies out, door closes behind you, hero reachable again

Check `prefers-reduced-motion` mounts no canvas, and that mobile still reaches
the doors.
